# V0.1.0 RTX 5090 Reference Feasibility

## Executive Result

**CONDITIONAL**

RTX 5090 32 GB에서 고정된 NVIDIA VoiceChat 11B checkpoint의 공식 loader는
적재되고 일반 offline speech-to-speech 출력도 생성했다. 그러나 공식 source는
BF16이 아니라 전 parameter를 FP32로 구성했으며, VRAM을 포화시키고 공식
function-calling sample에서 CUDA OOM이 발생했다. 일반 sample의 generation-only
RTF 추정치는 49.74였다.

별도 experimental mitigation에서 모든 floating parameter를 BF16으로 cast하고
CUDA autocast를 적용하면 일반 대화와 function channel이 모두 동작했다. 이때
일반 sample RTF는 2.39로 개선됐지만 실시간 기준 1.0을 통과하지 못했다. 공식
interactive container는 최소 80 GB VRAM, Docker Engine, NVIDIA Container Toolkit을
요구하므로 이 32 GB/비-container host에서 검증할 수 없었다.

## GPU and CUDA Compatibility

PyTorch 2.10.0+cu128 detected RTX 5090 capability `sm_120` and BF16 support.
CUDA allocation, BF16/FP16 matrix multiplication, BF16 SDPA, Triton 3.6.0,
causal-conv1d 1.6.2.post1 import, and Mamba2 BF16 forward passed. FlashAttention,
Transformer Engine, and vLLM were not installed in the official offline environment;
this is distinct from a kernel failure. No `unsupported sm`, `invalid device function`,
or `no kernel image` error was observed.

## Offline General Inference

R0 (`47c125f9-3dfd-4e33-9762-85558dbfa884`) used the pinned official script,
no quantization, no offload, and no model/checkpoint modification. The official
source constructed 11,068,552,672 FP32 parameters (44,274,210,688 parameter bytes),
not BF16. Load completed in 80.09 seconds. The 15.61-second official input produced
15.68 seconds of 22.05 kHz mono audio and a valid text response. Total cold wall time
was 860.08 seconds.

R3 (`89c19075-441b-471b-8480-88ff83857fd2`) is explicitly experimental. Full BF16
cast plus autocast produced the same text and duration in 37.50 seconds after an
82.73-second load.

## Offline Function Calling

R0 used the official `sample_fc.wav` and pre-written
`random_number_response.json`. No live tool side effect ran. It reached roughly
step 550/859 in pass 1 and failed with `cudaErrorMemoryAllocation` after 1,171.14
seconds, before a parseable committed result or spoken continuation.

R3 BF16 detected and parsed this envelope at step 95:
`generate_random_number({"min": 1, "max": 50})`. The mock response `{"result": 20}`
was injected at step 133, and speech resumed with “Your random number is twenty.”
Two-pass inference took 206.41 seconds. This proves interface survival under the
experimental dtype path, not tool accuracy.

R2 (`589f60d6-541b-4c6c-a290-3523d1d41655`) preserved a failed first mitigation:
changing only the construction default left 9.68B FP32 and 1.39B BF16 parameters,
then failed with a float-input/BF16-bias mismatch.

## Interactive Deployment

`BLOCKED: INTERACTIVE CONTAINER PREREQUISITES`.

The pinned NVIDIA documentation specifies `nvcr.io/nim/nvidia/nemotron-labs-voicechat:latest`
and model version `nim/nvidia/nemotron-labs-voicechat:1.0.0`, but the image reference
is floating and no digest could be resolved without a working container path. The
same documentation requires at least 80 GB VRAM and lists A100, H100, RTX 6000 Pro,
and B200. This server has 32 GB and lacks Docker/NVIDIA Container Toolkit. No host-wide
runtime installation was authorized, and hardware capacity would remain insufficient.

Therefore no container was launched and no WebSocket protocol version, loopback
TTFA, interruption, reconnect, or client/network latency was fabricated.

## VRAM Profile

| Run | Load/operation | Peak/result | Remaining physical VRAM |
|---|---|---:|---:|
| R0 | official FP32 load | allocator 44.47 GB; `nvidia-smi` 31,988 MiB | about 619 MiB |
| R0 | general inference | `nvidia-smi` 32,132 MiB | about 475 MiB |
| R0 | function calling | `nvidia-smi` 32,137 MiB then OOM | about 470 MiB |
| R3 | BF16 general | allocator 23.56 GB; `nvidia-smi` 23,465 MiB | about 9,142 MiB |
| R3 | BF16 function | allocator 23.74 GB; `nvidia-smi` 25,158 MiB | about 7,449 MiB |

The FP32 allocator value exceeds physical VRAM; WSL/CUDA memory behavior allowed load,
but inference reached the physical limit. FP32 cannot share this GPU with another
resident Memory/Codex model. BF16 leaves limited capacity, but co-residency remains
unvalidated and would reduce safety margin.

## Host RAM Profile

Model construction peaked near 61.8 GiB RSS in both FP32 and cast-based BF16 runs,
because R3 first constructs/loads the FP32 model on host before casting. Minimum
system-available memory during committed telemetry was about 16.7 GiB. A deployment
path must eliminate this transient peak before assuming safe multi-service startup.

## Latency

Interactive first-partial, TTFA, playable TTFA, interruption, and reconnect metrics
are **not measured** because the official interactive prerequisites failed before
server startup. Offline BF16 still needed 37.50 seconds for a 15.68-second response,
so it cannot substitute for a passing streaming latency result.

## Soak Test

No 30-minute interactive soak was run. The official container could not be started,
and the available offline paths already failed either function-call memory or the
real-time gate. Merely keeping a process alive would not satisfy the required repeated
inference/state-transition soak, so it is reported as blocked rather than passed.

## Feasibility Classification

**CONDITIONAL.** Offline interface viability exists only with an explicit experimental
BF16 modification, and even that path is slower than real time. The unmodified vendor
path does not sustain the official function sample. Interactive compatibility and
latency remain blocked by documented hardware/runtime prerequisites.

## Risk Register Updates

The measured before/after likelihoods and next mitigations are recorded in
`docs/risk-register.md`. Core Blackwell kernels are lower risk; VoiceChat capacity,
full-duplex latency, co-residency, and interactive-container access remain high risk.
Disk capacity is low risk for the next checkpoint/dataset planning step.

## Decision

1. **원본 VoiceChat 11B 적재:** yes for the vendor FP32 loader under WSL, but it is
   not BF16 and does not sustain the longer function sample.
2. **여유 VRAM:** roughly 0.47–0.62 GiB at FP32 peaks; 7.45–9.14 GiB for experimental BF16.
3. **실시간보다 빠른가:** no; best measured RTF is 2.3915.
4. **Interactive container RTX 5090 지원:** not demonstrated; pinned prerequisites
   require 80 GB and do not list RTX 5090.
5. **Full-duplex latency 충분:** unknown/blocked, with offline evidence unfavorable.
6. **Quantization 필수:** not proven mandatory for load, but a supported optimized
   low-memory/low-latency path is mandatory for service use.
7. **Memory/Codex GPU 동시 상주:** no for FP32; unvalidated and risky for BF16.
8. **파인튜닝 후 architecture 유지:** not justified until official streaming works.
9. **V0.2.0 Dataset Foundry:** may begin only as a data/governance track; do not treat
   RTX 5090 production deployment as solved.
10. **추가 hardware/service 분리:** yes; validate the official container on an 80 GB+
    supported GPU and plan voice/Codex resource separation.

## Next Stage

- Re-run the immutable NVIDIA container on a supported 80 GB+ GPU with Docker and
  NVIDIA Container Toolkit, resolving the image to a digest.
- Measure loopback TTFA/interruption/reconnect and a real 30-minute state-transition soak.
- Ask upstream for a documented BF16/FP8/quantized loader and a pinned nested remote-code revision.
- If RTX 5090 must remain the target, profile an upstream-supported low-memory path;
  do not promote the local R3 cast as reference behavior.
- V0.2.0 dataset governance work may proceed independently, without beginning training.
